# コスト考慮型モデル選択・分業ガイド

## 結論

フロンティアモデルを常時使用するのではなく、作業を次の順序で割り当てる。

1. LLMを使わず、決定的なツールで処理できるか確認する。
2. 明確に限定され、可逆的で、結果を機械的または短時間で検証できる作業は低コストモデルへ割り当てる。
3. 曖昧な判断、高い変更影響、大量または矛盾したコンテキスト、権限を伴う操作は上位モデルへ割り当てる。
4. 成果物確定、外部書き込み、Gitの変更操作など、既存規則で定めた人の承認はモデル階層にかかわらず維持する。

フロンティアモデルを必ず司令塔にすると、単純作業にも分解・指示・統合のコストが発生する。そのため、タスク全体を担当するモデルも、必要条件を満たす最小の能力階層から選ぶ。

## 能力階層

モデル名や提供元ではなく、次の能力プロファイルで表現する。

### Tier 0: 決定的ツール

LLMを使用しない。

適する作業：

- ファイル存在確認
- 静的検証ツールの実行
- テスト実行
- Gitの対象限定status・diff
- ハッシュ比較
- 形式変換や整形ツール
- 事前に定義された規則の機械的検査

同じ入力に対して同じ結果が得られる処理は、原則としてこの階層を優先する。

### Tier 1: 低コストモデル

入力、出力、禁止事項、検収条件を小さな作業票として明示できる作業を担当する。

適する作業：

- 指定されたファイルだけの要約
- 既存方針を変えない文章整理
- 明示された形式への書き換え
- 仕様が確定しているテストケースの追加
- 対象限定の差分説明
- contextへ登録済みのファイル一覧の点検
- 独立した複数ファイルに対する同種の検査

Tier 1は、新しい方針の決定、矛盾の最終判断、権限操作を行わない。

### Tier 2: 標準推論モデル

複数の制約を統合する必要はあるが、変更範囲が限定され、検収基準を定義できる作業を担当する。

適する作業：

- 既存設計に従った限定的な実装
- 失敗したテストの原因候補整理
- 複数の既知文書間の整合確認
- Tier 1成果物の意味的レビュー
- 中程度のタスク分解と統合

### Tier 3: フロンティアモデル

高い推論能力または広い文脈理解が必要な作業を担当する。

適する作業：

- 新しい管理方針やアーキテクチャの設計
- 指示、規則、成果物の矛盾解決
- Goalや必要コンテキスト自体が不明確な作業
- 失敗時の影響が大きく、検証が難しい変更
- セキュリティ、秘密情報、外部権限、不可逆操作に関する判断
- 複数モデルの結論が衝突した場合の裁定
- 本モデル選択方式自体の変更

### Human Gate

人の承認が必要な操作は、どのモデルも代替しない。

- WIP成果物の確定と`current/`への昇格
- 外部リソースへの書き込み
- 許可が必要なローカル保存またはGit登録
- branch、stage、commit、pushなど、既存規則で承認対象のGit操作
- 正とする成果物や方針を決める必要がある矛盾

## 振り分け手順

数値スコアを毎回記録すると管理コストが増えるため、次の短い順序で判断する。

1. 決定的ツールだけで完了できるならTier 0を使う。
2. 入出力と対象ファイルを正確に限定できるか確認する。
3. 誤りが発生しても容易に取り消せるか確認する。
4. 合否をツール、テスト、明示的チェックリストで確認できるか確認する。
5. 秘密情報、外部書き込み、Git変更操作、管理規則の変更を含まないか確認する。
6. 必要コンテキストが小さく、矛盾がないか確認する。

2から6をすべて満たすならTier 1を候補とする。一部に意味的判断が必要だが範囲と検収条件が明確ならTier 2を使う。それ以外はTier 3へ割り当てる。

能力が不明なモデルを、推測でTier 1またはTier 2として扱わない。小さな検証用作業で適合性を確認するか、上位階層を選ぶ。

## 分業用の最小作業票

低コストモデルまたは別エージェントへ委譲するときは、会話履歴全体を渡さず、次だけを渡す。

```markdown
Task ID: T-XXX
Subtask: <1つの具体的な作業>
Goal: <合格状態>
Allowed inputs:
- <contextへ登録済みの正確なファイル>
Allowed output:
- <専用WIPパス>
Do not:
- <禁止操作>
Validation:
- <コマンド、テスト、チェック項目>
Escalate when:
- <判断不能または失敗条件>
```

作業票は通常、実行時の指示として渡す。別セッションでの再開または検収に必要な場合だけWIP成果物として保存し、`context.md`へ登録する。

## 並列処理

プロジェクトの`active`タスクは引き続き1件とする。並列処理する単位は、activeタスク内部の下位作業であり、`tasks.md`へ別のactiveタスクとして追加しない。

並列化してよい条件：

- 下位作業の入力と出力が明確に分離できる。
- 各作業が別のWIPファイルまたは専用ディレクトリへ出力する。
- 同じファイルを複数の作業者が同時編集しない。
- 一方の結果が他方の前提になっていない。
- 統合方法と検収条件を先に定義できる。
- 作業票の作成、結果待ち、統合、再検証を含めても時間またはコスト削減が期待できる。

同一ファイルの分割編集、相互依存する設計判断、共通の未確定前提を持つ作業は並列化しない。

## 成果物の統合と検証

低コストモデルの出力を、そのまま承認済み成果物として扱わない。検証の深さは変更影響に合わせる。

### 低影響

例：形式修正、一覧生成、既知パターンの置換。

- Tier 0の検査を優先する。
- 検査に合格すれば、同じモデルによる再レビューは省略できる。

### 中影響

例：READMEの再構成、既知仕様に基づくコード変更。

- Tier 0のテストと差分確認を行う。
- 必要ならTier 2による意味的レビューを1回行う。

### 高影響

例：`rules.md`、管理ライフサイクル、権限、外部書き込み、安全制約。

- Tier 3が設計または最終レビューを担当する。
- 既存のHuman Gateを通す。

すべての下位成果物をフロンティアモデルが全文再読すると節約効果が失われる。機械検証結果、差分要約、失敗箇所を先に絞り、必要な部分だけを上位モデルが読む。

## エスカレーション条件

次のいずれかに該当したら、現在の階層で推測して続けず、上位モデルまたは人へ上げる。

- 必要な入力が作業票に含まれていない。
- 指示、入力、rulesの間に矛盾がある。
- 合否条件を満たせない、または検証が実行できない。
- 同じ原因による失敗が2回続く。
- 作業範囲外のファイル変更が必要になる。
- 新しいトップレベルディレクトリ、管理項目、ルールが必要になる。
- 秘密情報、外部書き込み、破壊的操作、Git変更操作が必要になる。
- 複数の下位成果物が矛盾する。
- 不確実性が成果物の正しさへ影響する。

エスカレーション時は、会話全体を渡すのではなく、作業票、確認済み事実、失敗結果、必要な判断だけを渡す。

## 利用環境への適応

環境によっては、エージェントごとのモデル選択、並列実行、使用量取得ができない。この場合は、利用可能な機能だけを使う。

1. Tier 0の決定的ツールは可能な限り利用する。
2. モデル選択が可能なら能力階層を対応付ける。
3. 自動選択できない場合は、人がモデルを選ぶか、別セッションへ作業票を渡す。
4. 並列実行できない場合は、同じ作業票を順番に実行する。
5. 使用量を取得できない場合は、入力ファイル数、入出力文字量、所要時間、人のレビュー時間を代替指標にする。

モデル名と階層の対応は変化しやすいため、`rules.md`や共通テンプレートへ固定しない。

## 評価方法

同じ種類の小規模作業を、従来方式と振り分け方式で比較する。

代表作業候補：

1. 静的検証と結果要約
2. READMEの既存方針を変えない文章整理
3. 明確な仕様に基づくテスト追加
4. rules間の矛盾を含む設計判断

記録項目：

- フロンティアモデルの使用回数
- フロンティアモデルへ渡した入力・出力量、または利用クレジット
- 全モデル合計の入力・出力量、または利用クレジット
- 経過時間
- 人のレビュー時間
- テストまたは静的検査の失敗数
- 意味的な誤りと再作業回数
- rules違反または範囲外変更の有無

削減率だけでなく、再作業を含めた総コストで比較する。品質、安全性、承認規則に違反した試行は、コストが低くても不採用とする。

## 初期評価からの知見

テンプレート設計時の小規模比較では、必要な規則と検収条件を明示した限定作業について、低コスト、標準推論、上位モデルの間で品質差を検出できなかった。一方、必要なプロジェクト規則を作業票へ含めなかった場合は、すべての階層が同じ誤判断をした。

この結果から、上位モデルを使うことだけではコンテキスト不足を補えず、委譲用作業票の完全性がモデル階層より重要であると判断した。導入当初は3階層を使い、実作業の品質、再作業、エスカレーション、所要時間を記録する。低コストモデルと標準推論モデルに実質的な品質差がなければ、2階層への簡略化を検討する。

利用環境でモデル別使用量を取得できない場合は、入出力量を代理指標とし、根拠日を明記した類似サービスの価格比で相対コストを試算する。モデル固有の名称、価格、コンテキスト上限は変化するため、このガイドへ固定しない。
