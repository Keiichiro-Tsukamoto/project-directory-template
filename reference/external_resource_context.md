# 外部リソース・コンテキストガイド

## 基本方針

外部リソース1件につき、原則として`reference/external/`へ参照記述ファイルを1件置きます。`context.md`には外部URLではなく、このローカルファイルを登録します。

リソースは、サービス、ワークスペース、リソース種別、リソースIDの組み合わせで識別します。表示名とURLは変更される可能性があるため、補助情報として扱います。

範囲の限定された集合を常に一緒に使う場合を除き、1件の参照記述で複数リソースを表現しません。ドライブ、サイト、フォルダ、ワークスペース全体を登録しません。

参照記述は`reference/external/_template.md`のフィールド形式を維持します。参照記述を作成または更新したら、contextへ登録し、外部内容の取得やcache利用より前に`validate_template.py`を実行します。標準外の自由形式記述を、外部リソースへのアクセス許可や正規入力として使用しません。

`変更性: mutable`は内容が同じリソースIDのまま更新されうるリソース、`immutable`は内容が固定された特定版を表します。表示名、URL、cacheの存在だけで変更性や現在版を判断しません。

## 取得モード

### live

鮮度境界で最新版を確認します。mutableなリソースでは、現在の更新指標とcache側の値が一致した場合だけcacheを再利用できます。

revision、updated-atなどを本文と独立して確認できる場合は、最初に更新指標だけを取得します。更新指標が一致すれば、内容本体を再取得しません。利用可能な更新指標がなく、安定した対象範囲hashも確認できない場合だけ、`鮮度確認方法: refetch`として内容を再取得します。

### pinned

`期待するリビジョン`と一致する版だけを取得します。指定版を取得または検証できない場合、最新版へ置き換えず作業を停止します。

### snapshot

ローカルの固定スナップショットを使用します。参照記述とスナップショットの両方を同じTask IDで`context.md`へ登録します。`ローカル保存`が`禁止`なら使用できず、`要承認`なら保存前に人の承認が必要です。

snapshotは特定時点版であり、リモートの現在版と同じとは主張しません。

## 鮮度境界

mutableな外部リソースは、次の時点で現在版との一致を確認します。

- タスク開始または再開後、最初に利用するとき
- 別モデルまたは別環境へ引き継いだ後
- 外部内容に基づく検証、重要な判断、成果物確定の直前
- 人から外部リソースが更新されたと通知された後
- 外部リソースへ書き込む直前

同じ作業内で現在の更新指標を再確認でき、前回取得時と一致する場合は、内容本体を再取得する必要はありません。

## 鮮度確認、内容取得、LLM入力

次の3段階を分けて判断します。

### 1. 鮮度確認

登録されたリソースIDと取得範囲に対して、本文を取得せず確認できる最小の更新指標を優先します。

1. サービスが提供するrevision、version、ETag
2. 本文と独立して取得できるupdated-at
3. 登録された取得範囲の安定したcontent-hash
4. refetch

上位の方法を利用できる場合、安全上の理由なく下位の方法を既定にしません。`refetch`は、現在版との一致を示す指標を取得できない場合の最終手段です。

### 2. 内容取得

現在のリモート更新指標とcache側の値が一致する場合、内容本体を再取得しません。

更新指標が不一致の場合は、ファイル、サイト、ワークスペース全体ではなく、参照記述の`取得範囲`だけを取得します。サービスの更新指標がリソース全体に対する値で、取得範囲外の変更でも値が変わる場合は、取得範囲を前回と同じ方法で正規化してhashを比較できます。

異なるエクスポート形式、列順、文字コード、改行、数式と表示値など、表現方法が異なるデータのhashを同一条件として比較しません。正規化方法が安定しない場合は、hash一致を根拠に取得を省略しません。

### 3. LLM入力

リモート取得またはcache確認の結果を、そのまま全量でLLMへ入力しません。Goalに必要な登録範囲だけを入力します。

- 同一セッションで必要内容が利用可能で、更新指標も一致する: 同じ内容を再入力しない。
- 別セッション、別モデル、別環境で、現在版と確認済みのcacheがある: Goalに必要な部分だけを入力する。
- リモート更新指標は変わったが、正規化した取得範囲hashが一致する: 同じ範囲を再入力しない。
- 取得範囲の内容が変わった: 変更箇所とGoalに必要な周辺だけを入力する。差分だけでは意味が確定しない場合は、必要な範囲全体を入力する。
- cacheを現在版と確認できない: cache本文を入力せず、再取得または停止する。

cacheが同一版であることは正しさの条件です。LLMへ再入力しないことはトークン最適化であり、同一版確認を省略する理由にはなりません。

## cacheの再利用

cacheの保存が許可されていることと、cacheを現在の正規入力として再利用できることは別です。

- `禁止`: cacheを入力に使わず、リモートから取得します。
- `同一版確認時のみ`: 現在のリモート更新指標とcache側の更新指標が一致した場合だけ再利用します。
- `固定スナップショットのみ`: `取得モード: snapshot`でcontext登録済みの固定snapshotだけを使用します。

本文と独立してrevisionまたはupdated-atを確認でき、ローカル保存が許可されるmutableリソースでは、原則として`キャッシュ再利用: 同一版確認時のみ`を選びます。機密性、保存方針、利用環境の制約によりcacheを保持できない場合は`禁止`を選べます。

本文と独立して更新日時を取得できるmutableなliveリソースの標準例は次のとおりです。

```text
変更性: mutable
取得モード: live
鮮度確認方法: updated-at
キャッシュ再利用: 同一版確認時のみ
検証不能時: 停止
```

「cacheが存在する」「以前アクセスできた」「表示名が同じ」「ファイルIDが同じ」だけでは、現在版とみなしません。

`鮮度確認方法: refetch`ではcacheとの同一版を証明できないため、`キャッシュ再利用: 禁止`を指定します。リモート確認も再取得もできなければ、cacheを現在版として使わず停止します。

## 一時状態とエビデンス

更新指標、取得日時、本文取得の有無、対象範囲hash、LLM入力の範囲、cache一致、エラーは、`reference/external/_state_template.md`を基に`wip/T-XXX/.tmp/external-state/`へ記録します。この場所はGitとcontextの対象外です。

静的な参照記述へ、毎回変わる確認日時や更新指標を書き戻しません。

検収、再現、外部更新の証跡に必要な情報だけをWIPエビデンスへ移し、contextへ登録します。

## エラーと代替手段

アクセス不能またはrevision検証不能の場合、Web検索、類似文書、未登録cacheへ置き換えません。

`検証不能時: 停止`では、現在版を必要とする作業を停止します。`検証不能時: 登録スナップショットを旧版として使用`かつ`代替手段: local-snapshot`で、登録済みsnapshotがある場合だけ代替できます。

古いsnapshotを使う場合は、現在版を確認できなかったことと特定時点版を使ったことを成果物へ明示します。現在版との一致がGoalの合否に必要なら、snapshotでは代替せず停止します。

必要なコネクタがない環境では、コネクタへのアクセスまたは明示的に登録されたスナップショットを人へ依頼します。

## 外部更新

外部アクセスは読み取り専用が標準です。変更案は`wip/`で作成し、対象と操作について人の承認を得ます。書き込み直前にリビジョンを再確認し、変更されていた場合は上書きしません。反映後は新しいリビジョンと内容を確認します。

作業環境に編集権限がない場合、承認済み成果物を`current/`へ移して引き渡しタスクを完了し、リモート反映を別作業または別タスクにできます。リモート旧版とローカル承認版が食い違う場合、正とする版を人へ確認します。

## 保存と秘密情報

外部リソースを閲覧できても、ローカル保存またはGit登録が許可されているとは限りません。参照記述の各項目を確認し、`要承認`または不明なら人へ確認します。

アクセストークン、セッション情報、認証情報、有効期限付き署名URLその他の秘密情報を、参照記述、スナップショット、管理ファイル、成果物、ログ、Gitへ保存しません。

## 静的検証の限界

`validate_template.py`は、contextへ登録された参照記述のスキーマ版、構造、値、取得モードと鮮度・cache方針の組合せ、snapshot登録などを検査します。

外部サービスへの接続、実際の権限、現在のリモート更新指標、取得時点、cache一致、本文取得の要否、対象範囲hash、LLM入力範囲、Git追跡状態は実行時または人による確認が必要です。静的検証の合格だけで、cacheが現在版であるとは判断しません。

## 旧形式の移行

旧形式や自由形式の参照記述は、次に外部内容を利用する前に移行します。

1. 独立したリソースごとに参照記述を分割する。
2. `_template.md`へ識別子、範囲、権限、保存方針を移す。
3. 変更性、鮮度確認方法、cache再利用、検証不能時の扱いを人へ確認する。
4. contextを新しい参照記述へ更新する。
5. `validate_template.py`を実行する。
6. 合格後に外部内容を取得またはcache再利用する。

移行前の記述や、現在版との一致を確認できないcacheを、現在の正規入力として使用しません。

schema v2の参照記述は、このガイド更新だけを理由に変更する必要はありません。既存の実行時状態記録も移行不要です。
