# Project Directory Templateへのフィードバック

## 目的

本テンプレートを実際に利用して起きた事象を、機密情報を含まないGitHub Issue用の下書きへ整理します。下書きの作成と外部投稿を分け、人が内容を確認する前に投稿しません。

## LLMへ渡す短い指示

> このテンプレートの利用フィードバックを作成してください。`reference/product_feedback.md`に従い、実際に起きた事実と改善提案を分け、機密情報を除いたGitHub Issue用の下書きをWIPに作ってください。GitHubへの投稿は行わないでください。

## 作成手順

1. 現在の`rules.md`とタスク状態に従い、activeタスクを勝手に置き換えません。
2. 人が提供した事実と、active Task IDでcontextへ登録された必要なファイルだけを使います。フィードバック作成のためにプロジェクト全体を走査しません。
3. 分からない版、環境、発生条件、結果を推測で補いません。不足が結論に影響する場合だけ人へ確認します。
4. 観測事実と、LLMまたは人による原因推定、改善提案、優先度を分けます。
5. 問題が複数ある場合は、最初にWIPの`feedback_triage.md`へ一覧化し、下記の基準でIssue候補へ分けます。
6. Issue用MarkdownをactiveタスクのWIPへ作ります。GitHubへ投稿せず、人へレビューを依頼します。

activeタスクが別の作業を行っている場合は、そのタスクを中断せず、フィードバック作成タスクの開始方法を人へ確認します。

## 複数の問題の扱い

1件のIssueには、受け手が一つの変更と検証で完了判断できる問題だけを含めます。同じ原因、同じ変更対象、同じ受入条件で解決できる観測事実はまとめられます。原因、変更対象、期待する結果が異なる問題を、件数を減らすためだけに混ぜません。

問題が複数ある場合、LLMは次の順で扱います。

1. すべての観測事実を`feedback_triage.md`へ重複なく列挙する。
2. 同じ原因・変更・検証で扱える項目を一つのIssue候補へまとめ、分割理由または統合理由を示す。
3. 影響、再現性、回避策の有無、根拠の確かさから、先に確認する候補を提案する。言及順や文章量を優先度の根拠にしない。
4. 一度に作るIssue下書きは最大3件とする。残りは`feedback_triage.md`へ未提出候補として残し、Issue下書きを自動作成しない。
5. 人が投稿対象を選んだIssueだけをレビュー対象にする。複数の下書きが承認されても、外部投稿の対象と件数を改めて確認する。

人が明示的に件数を指定した場合を除き、4件以上のIssue下書きやIssueを一度に作りません。分割基準が定まらない場合は、問題を混ぜたIssueを作らず、`feedback_triage.md`を人へ提示して判断を求めます。

`feedback_triage.md`は次の最小形式にします。

```markdown
| 候補 | 観測事実 | 影響 | 再現性 | 回避策 | 統合・分割理由 | 状態 |
|---|---|---|---|---|---|---|
| F-001 |  |  |  |  |  | 下書き候補／未提出 |
```

## Issue下書き（1問題につき1ファイル）

```markdown
# <事象が分かる短い件名>

## 利用環境

- テンプレート版：<分かる場合だけ>
- LLM環境：<製品、モデル、実行環境。分かる場合だけ>
- 対象作業：<事象が起きた作業>

## 実際に起きたこと

<観測できた事実。推測や提案を混ぜない>

## 期待したこと

<期待した挙動または結果>

## 発生条件または再現手順

<確認済みの最小条件。不明な場合は「未確認」>

## 影響と回避策

<作業への影響と、実際に有効だった回避策。なければ「なし」>

## 原因の推定（任意）

<推定であることが分かるように記載>

## 改善提案（任意）

<観測事実と分離して記載>

## 公開前確認

- [ ] 機密情報、個人情報、認証情報、非公開URL、顧客データを含まない
- [ ] 観測事実と推定・提案を分けた
- [ ] 入力にない実行、検証、完了状態を作っていない
- [ ] 外部投稿について人が確認した
```

## 投稿

投稿先は[Project Directory TemplateのGitHub Issues](https://github.com/Keiichiro-Tsukamoto/project-directory-template/issues/new)です。

GitHubへアクセスできない環境では、承認済みMarkdownを人へ渡します。アクセスできる場合も、下書きの承認を外部投稿の承認とみなさず、Issue作成について明示的な許可を得てから投稿します。
