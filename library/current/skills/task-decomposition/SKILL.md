# タスク分解と実行

抽象度の高い依頼や規模の大きい成果物ほど、一度で作り切るのは難しい。分割統治法と同じく、問題を分割し、一つずつ解いて最終ゴールに至る。

依頼を受けたら、次の順に進める。

1. 分解するかを決める
2. タスクに分解する
3. 依存関係をDAGで表す
4. 承認が要るチェックポイントを人に聞く
5. イベントの伝え方を決める
6. 実行する
7. 定期的に状況を確かめる
8. 実行できない・計画に誤りがあるときに組み直す
9. 最終ゴールで終える

## 1. 分解するかを決める

次の二つを見る。

- **中間成果物が発生するか。** 最終成果物を作る前に、別の成果物を作って次の工程で使うか。例：報告書を書く前に、調査メモやデータの集計表を作る。
- **最終成果物を複数作る必要があるか。** 例：報告書と、その要約のスライドの両方を渡す。

どちらかに当てはまれば、最終工程までに成果物が複数発生する。それぞれを作るところまでがチェックポイント（マイルストーン）なので、分解する。

どちらにも当てはまらなければ、分解せず、4.の承認も聞かずにそのまま作る。例：一通のメールの誤字を直す。

実行を始めてから、メモや調査結果などの細かい中間成果物が出ることもある。それもチェックポイントになり得る。チェックポイントにするなら、それを作る工程も2.と同じくタスクとして扱う。

## 2. タスクに分解する

各中間成果物・最終成果物を作る工程のすべてを、タスクまたはサブタスクとみなして分解する。分けた各タスクにも1.の二つの基準を当て、当てはまればさらにサブタスクに分ける。当てはまらなくなったら、そこで止める。

タスクごとに、作る成果物と、その前に要る成果物と、担当（自分／サブエージェント／他のエージェント）を書く。

例（市場調査の報告書と要約スライドを作る依頼）：

| タスク | 作る成果物 | その前に要る成果物 | 担当 |
|---|---|---|---|
| T1 資料を集めて読む | 調査メモ | なし | サブエージェント |
| T2 販売データを集計する | 集計表 | なし | サブエージェント |
| T3 報告書を書く | 報告書 | 調査メモ、集計表 | 自分 |
| T4 要約スライドを作る | 要約スライド | 報告書 | 自分 |

## 3. 依存関係をDAGで表す

あるタスクが別のタスクの成果物を使うなら、その間に依存の矢印を引く。上の例は次のDAGになる。

```
T1 調査メモ ─┐
             ├─→ T3 報告書 ─→ T4 要約スライド
T2 集計表 ───┘
```

依存のあるタスクは、前のタスクの成果物ができてから始める。例では、T1とT2には依存がなく、T3はT1とT2の成果物ができてから始める。

## 4. 承認が要るチェックポイントを人に聞く

すべてのチェックポイントを人が承認すると、人の負荷が高い。依頼を受けたら、実行を始める前に、どのチェックポイント・マイルストーンで承認が要るかを人に聞く。例：「調査メモ、集計表、報告書、要約スライドのうち、確認してから先へ進めたいものはどれですか」。サブエージェントとしてこのスキルを読んだときは、人の代わりに依頼元に聞く。

承認は、そのチェックポイントの後ろに置くDAGの節として扱う。承認に依存するタスクだけが待つ。

## 5. イベントの伝え方を決める

前のタスクの完了、人の返事、決まった時刻など、イベントを待って始まるタスクでは、キックが届かない・消えることがある。そこで、6.でタスクを渡す前に、伝える手段とサブエージェントとのインターフェースを確実に決める。決める項目は次のとおり。

- 誰が誰に知らせるか
- どの手段で知らせるか（例：返信、共有ファイルへの書き込み）
- 何を知らせるか（例：終わったタスク、成果物の置き場所）
- いつ知らせるか（例：成果物ができた時点）
- 知らせが来ていなければおかしい時刻（期限）

届かないことは、7.の定期確認で見つける。

## 6. 実行する

依存のないタスクは、サブエージェントや他のエージェントに分けて並列に実行する。

サブエージェントや他のエージェントがいない環境では、DAGの順に一つずつ自分で実行する。

## 7. 定期的に状況を確かめる

頻繁でなくてよいので、時間ベースで定期的にイベントと進捗の状況を確かめ、イベントが落ちていないかを見る。見るのは次の二つである。

- 知らせの期限を過ぎたのに、知らせが来ていないイベントはないか。
- 前のタスクの成果物が置き場に実物であるのに、まだ始まっていないタスクはないか。

途中から読んだときも、3.のDAGと5.の決め事を確かめてから、この二つを見る。

期限を過ぎていたら、知らせる側に一度だけ確かめる。それでも返事がなければ、依頼元に伝えて判断を仰ぐ。成果物がすでにあれば、次のタスクを始める。ただし、4.で承認が要るとされた所の後ろのタスクは、承認が済むまで始めない。

サブエージェントの終了は環境の通知に任せ、定期確認では、人の返事、他のエージェントの完了、時刻など、その通知が届かないイベントを見る。サブエージェントが終了を知らせない環境では、終了も定期確認で見る。

エージェントは起こされたときしか動けないので、決まりに書くだけでは確認は起きない。使える環境では、定期実行の仕組みで動かす。定期実行のない環境では、タスクの区切りごとに状況を見直す。

## 8. 実行できない・計画に誤りがあるときに組み直す

タスクが実行できなくなったとき、または計画の誤りに気づいたときは、次の順に組み直す。知らせが来ないだけのときは、7.のとおりにする。

- **問題のタスクと、親へ返すゴールを確かめる。** 3.のDAGで、実行できなくなったタスク、または誤りのあるタスクを見つける。これを問題のタスクと呼ぶ。問題のタスクを2.で分けた元のタスクが親である。親へ返すゴールは、問題のタスクが作る成果物の機能と品質である。それを使う後続のタスクが何を必要としているかから、後続のタスクがなければ依頼から読み取る。
- **配下で組み直す。** ゴールを満たすように、問題のタスクの配下で2.と3.をやり直す。
- **配下で満たせなければ上げる。** 分かれ目は、配下の組み直し案でゴールの機能と品質を満たせるかである。満たせる案が作れなければ、親に上げる。親のゴールを確かめ直し、親の配下で組み直す。必要なら繰り返し上げる。最上位の依頼そのものでも満たせないとき、または組み直しが自分の受け持ちの外に及ぶときは、依頼元に返して相談する。
- **DAGと成果物を直す。** 組み直した部分のDAGを、3.のとおり描き直す。そのまま活かせる成果物は残す。不要になった成果物はアーカイブする。参考に読むのはよい。
- **見直しの間の扱い。** 問題のタスクの成果物を使う後続のタスクは、見直しが終わるまで始めず、先へも進めない。組み直しで、承認が要るチェックポイントが変わったら、4.のとおり聞き直す。承認済みの成果物を組み直しで直したら、承認を取り直す。

例：2.の例で、T2で販売データが手に入らず、T2が実行できなくなる。T3は止まって見えるが、問題のタスクはT2である。親へ返すゴールは、T3の報告書に要る数値である。T2の配下ではこの数値をそろえられないので、親、ここでは依頼そのものに上げ、集計表の代わりになる成果物と、それを使うDAGを組み直す。それでも報告書を満たせなければ、依頼元に返して相談する。T1の調査メモはそのまま残す。

## 9. 最終ゴールで終える

分解した者が、すべての最終成果物がそろい、4.で承認が要るとされた所の承認が済んでいることを確かめてから終える。定期確認を動かしていたら止める。
