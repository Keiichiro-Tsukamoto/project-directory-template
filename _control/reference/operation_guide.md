# 運用詳細ガイド

必要な節だけを読む。[共通規則](../rules.md)が作業範囲・承認・配置の原本である。以下の相対パスは、選択した管理範囲を基準にする。管理タスクでは`workspace:_control/`、projectタスクでは当該projectが基準となる。

## タスクの登録と切替

入力は依頼、選択範囲の`tasks.md`・`context.md`、対象のタスク詳細。変更するのは対象行・詳細だけとする。

1. 未登録の依頼では、その範囲で未使用のTask IDを割り当て、`wip/`に`Background / Purpose / Goal / Notes`を持つ詳細を作り、`pending`行を追加する。登録自体のための別タスクは作らない。
2. 登録だけなら既存activeを維持して終了する。開始指示があれば、同じ範囲のactiveを調べる。複数なら矛盾を示して停止する。
3. 別activeがあれば中断または完了の扱いを確認する。中断の指示後に理由・再開条件をNotesへ残し、既存をblockedにする。入力行は保持する。完了する場合は[完了手順](#タスク完了時の確認)を先に終える。
4. 目標・開始に必要な入力条件が明確で、他activeがなく、開始を依頼されている場合だけ新タスクをactiveにする。不足時はpendingのまま必要情報を求める。
5. 再開は停止理由の解消と他activeがないことを確認して行う。以前の中断指示を、無条件の自動再開指示とみなさない。

終了条件は、同一範囲のactiveが最大一件で、登録・中断・開始の実際の状態と報告が一致すること。

## 入力不足と引継ぎ

不足情報、必要な理由、受入可能な形式を人へ示す。正確な既存パスが得られたらcontext登録後に読む。入力作成を別タスクにする場合は[登録と切替](#タスクの登録と切替)に従う。独立して進められるWIP作業まで止めない。

引継ぎには、確認済み状態、未解決事項、次の操作、登録済みの正確なパスをNotesへ残す。長い場合だけWIPの引継ぎ資料へ分離する。会話履歴や全入力の複製で代用しない。次タスク未確定の未解決事項はpending詳細へ残す。

完了タスクを再利用する場合、指定されたtasks行のDetailから成果物の最終配置を確認する。記録先がなければパスを人へ確認する。古い成果物を最新版と推測しない。

## タスク定義の更新

意味を変えない事実訂正・明確化はWIPで行える。目的、必要成果、重要な範囲、完了条件、承認済み方針が変わる場合は、根拠・変更・後続への影響を示して承認を得る。別の問題を解く場合は別タスクとする。

意味変更を承認された時だけNotesへ短く根拠・変更・影響を残す。完了時は最後に承認された目標で検収する。project.mdの目的・目標にも同じ判断を適用する。

## project間の固定複製

利用側projectのタスクが所有する。入力は元の正確なファイル、必要範囲、保存許可。全project共通への昇格とは別の操作である。

1. 元ファイルを一時的な入力としてcontextへ登録し、必要な部分だけをWIPへ複製する。周辺ファイルが必要なら正確なパスを追加登録する。project全体を無条件に複製しない。
2. 元へのリンクや実行時依存を確認する。必要な実体を含められなければ独立複製と判定せず、不足を示す。保存不可の場合も、直接参照の例外か別の入力を人へ確認する。
3. 元のパス、取得時点、確認できた版情報、保存制限を短い由来記録に残す。計算していないハッシュは書かない。内容同一性が要件なら使える確認手段で検証し、確認不能ならその要件を合格にしない。
4. 複製内容と配置先の承認後、利用側の`reference/`へ配置し、複製・由来記録をcontextへ登録する。元への一時入力と、解消した依存行を整理する。出典情報は消さない。
5. 更新依頼があった時だけ新しい複製候補を作り、差分・適合を確認して承認後に切り替える。旧複製の利用側があれば[参照保護](#参照元の削除移動置換)を先に行う。元資料の変更は自動反映しない。

元が消えても確認済み固定版は使えるが、現在版の確認はできない。複製が消失した場合に別ファイルで暗黙に代用しない。複製の変更を元projectへ反映したと報告しない。

## 共有依頼と依存更新

`library/`は全project共通とする。少数projectで使うだけなら[固定複製](#project間の固定複製)を用いる。

全project共通への昇格が依頼された場合、元projectで候補を作り、管理タスクのpending行・詳細・実在する入力を登録できる。これは共有成果物の承認・反映ではない。元projectの完了前に、後続が使う候補を`workspace:_control/wip/`へ引き継ぎ、参照を更新する。管理側が候補を受け取ったことを確認してから元の入力行を整理する。

自成果物の依存行と依頼済みの共有検討の登録だけは、projectタスクから行える。既存の管理activeや他タスクの行を変更しない。共有表への書込み前に、実効的な排他または他の書込みを止めた単独運用を確認する。確認できなければ登録案だけを元WIPに残す。

dependenciesの列は`Consumer / Source`。どちらも既存ファイルまたは不可分な成果物ディレクトリを`workspace:`付きで指定する。別範囲の実体への継続依存だけを一組一行で記載する。固定複製が独立していれば元への存在依存は不要。由来・最新追随・内容の妥当性をこの表で表さない。

共有候補の現行化は管理タスクの承認後に行う。候補は管理WIP、完了記録は管理archive、共有成果物の現行版・旧版はlibraryまたはprofileのcurrent・archiveへ置く。

## 参照元の削除・移動・置換

この手順はチャット経由の操作前検査であり、Finder等の直接削除を阻止するものではない。

1. 変更対象を正確なパスで示し、検査から反映まで競合しない排他または単独運用を確保する。
2. `workspace:projects/`直下の名前、ルートと各projectのtasks.md・context.md、ルートdependencies.mdを読む。この操作に限る横断読込であり、業務本文は読まない。
3. tasksの状態とcontextのTask IDを照合し、未完了タスクの入力と永続依存を探す。表の欠落・壊れた行・解釈不能・未取得を参照ゼロにしない。
4. パスの親子関係で比較する。対象内の参照だけでなく、対象を含む成果物ディレクトリへの依存も影響候補にする。文字列の先頭一致だけで隣接名を一致させない。
5. 参照があれば、関係する利用側だけを確認し、維持・旧版保持・参照切替・固定複製等を提案する。利用側の切替はその所有タスクと必要な承認を通す。無関係のタスクは止めない。
6. 同じタスクの入力を移動する場合も候補に現れる。自分の参照というだけで無視せず、移動後パスへの切替を操作計画に含める。他範囲の参照を勝手に書き換えない。
7. 反映・参照更新後に実在と状態を再確認する。途中失敗時は残る参照と実施済み操作を記録し、完了と報告しない。

## projectの作成と初期化

作成依頼は作成操作の承認とする。Project IDが未指定なら候補を示して人に決めてもらい、既存の同名ディレクトリを上書きしない。

管理タスクで`projects/<project-id>/_control/`、wip、current、reference/external、archive/discardedを用意する。project.mdはBackground・Purpose・Goalを「未設定」、tasks.mdはT-001（初期化）のpending行、context.mdは空表とする。project用rules.mdは作らない。

初期化の開始も依頼済みなら対象projectへ移り、T-001で人から背景・目的・目標を得てWIPに定義案を作る。承認後にproject.mdへ反映し、完了承認後にT-001を閉じる。目的未設定のまま別の業務タスクを始めない。管理タスクの完了とprojectのT-001開始は別の状態変更である。

## projectの取込と持出し

取込は人が領域内へ用意した正確な入力から管理WIPで候補を作る。新旧ID、独自制約、参照先、同名衝突、既存ソース構造を確認する。既存projectのrulesに独自条項がある場合、黙って廃棄せず共通条項との差分をproject.mdの制約候補にする。反映は承認後に行う。

分離・持出しの計画だけを依頼された場合は、対象projectの定義と管理表、必要な参照保護の確認から始める。定義・詳細・成果物は共通規則に従い登録して読む。既知の参照から計画できる場合は、配下の全ファイル名を列挙しない。収録物の全件確認が未実施なら、その点を計画に残す。

資料一式の準備、または収録漏れの確認を依頼され、一覧が必要な場合に限り、対象ディレクトリと一覧取得の目的を管理タスクの詳細へ記録して、その範囲のファイル名を取得できる。対象外のprojectや作業領域外へ範囲を広げず、リンク先もたどらない。名前の取得を本文読込の許可とせず、本文は必要なファイルだけ登録して読む。一覧だけでは内容・機密性・単独利用の可否を確認済みとしない。

持出しは管理WIP内に資料一式と手順を作るところまでとする。依存する共有規則・ガイド・資料を必要分だけ同梱し、領域内参照が切れないか確認する。単独実行できる形への変換が未検証なら「単独利用可能」と報告しない。領域外への移動を実行しない。

project削除は、対象IDと削除範囲の承認、未完了タスクの扱い、[参照保護](#参照元の削除移動置換)を確認してから行う。削除不可なら管理archive/discarded配下へ隔離し、参照先を解決してから通常project一覧から外す。

## 共通規則の更新

対象は共通規則・共通ガイド・管理プログラムである。文言だけの変更も管理タスクで扱い、次の順に進める。

文案・比較だけの依頼では、候補と未確認事項を示した段階で返してよい。反映の判断に必要な案を求められた場合、または自ら反映承認を求める場合は、次の手順2まで行う。反映可否を左右する未確認事項が残る場合は、その不足を示し、反映準備が整ったとは報告しない。

1. 現行ファイルを入力登録し、管理WIPで候補を作る。影響確認に限り、project名と各tasks.mdから未完了タスクを列挙できる。影響候補の正確な定義・詳細・入力だけを追加登録して確認する。
2. 承認を依頼する前に、変更対象、影響する管理タスク・project、確認済み範囲と未確認事項、検証方法、旧版の保管先と復元先をWIPに示す。共通資料を読込済みのセッションへ更新は自動反映されないため、再開時に何を再読するかも示す。
3. 対象と反映の承認後、実効的な排他または他の書込みを止めた単独運用と、[参照保護](#参照元の削除移動置換)を確認する。旧版を保持して共通一か所へ反映し、project固有資料を一括上書きしない。
4. 反映結果を検証し、失敗時は事前に示した範囲で復元する。復元できない場合は実施済み操作と残作業を記録して止める。未検証の利用側を確認済みと報告しない。

## レビュー、指示、意思決定の分離

「A案はGがなければ成立しない」はレビューであり、「G付きA案の採用」ではない。「A案を採用し、Gを満たすこと」のように選択を明示した場合だけ採用として扱う。

修正指示はWIPの修正を許すが、成果物確定や外部操作の許可へ広げない。明示的な承認依頼への「OK」は直前の対象と操作に限る。一部への回答を全体承認にしない。未決定を維持したまま可逆的な検討を進め、意思決定が必要な操作の直前でだけ確認する。

## タスク完了時の確認

1. 最後に承認された目標と実際の成果を照合する。実施していない試験を合格にしない。
2. 現行化・配置・削除・完了の承認対象を確認する。[共通規則の配置表](../rules.md#2-所有範囲とパスを固定する)に従って移動先を決める。
3. [参照保護](#参照元の削除移動置換)と後続への引継ぎを行い、成果物・旧版・制作記録を分けて配置する。
4. 不要物は削除可能なら承認範囲内で削除し、削除不可なら所有範囲のarchive/discarded/<Task ID>/へ移動する。再試行せず、隔離物をcontextへ登録しない。
5. Notesへ再利用対象の成果物の最終配置を記録し、詳細をarchiveへ移してtasksのDetailと残る入力・依存先を更新する。
6. 対象タスクのWIP残存、壊れた参照、未引継ぎ事項を確認する。対象context行を除きStatusをdoneにする。
7. 反映結果を再確認し、成果物・実施した検証・未確認事項を報告する。途中失敗ならdoneと報告せず、状態不一致を記録して修復する。

必要性や保存義務が不明な資料は、不要物と決めつけて削除・隔離しない。対象と不足する判断を示し、保持したまま確認する。

## 手動確認と自動検証

通常操作はMarkdownの読書きで行う。自動検証が使えなければ、対象行、実在、同一範囲active件数、移動前後の参照を手動で確認し、その範囲だけを報告する。機械的な完全性・厳密な同一性・並行書込みの安全を手動確認だけで保証しない。確認できない条件に依存する操作だけを止める。

作業領域の管理表を一括確認する場合は、[管理表の検査手順](../tools/shared_operations/README.md#管理表の検査)を読む。これは管理表と登録先の構造検査であり、業務本文や外部サービスの確認ではない。

## 並行操作の保護

操作入口は`workspace:_control/tools/shared_operations/manage.py`。利用前に[共有管理操作の手順](../tools/shared_operations/README.md)を読む。

対応操作は依存追加、projectのactiveタスクへの入力追加、未参照の`library/current/`内単一ファイルの削除・置換。対応操作では`prepare`でWIPへ案を保存し、依頼・承認範囲と一致することを確認して`apply`する。ロックは適用処理内で取得する。未完了変更は手順内の復元操作を使う。

タスク状態変更、入力解除、依存解消、管理タスク登録、複数ファイルの変更は単独実行する。独立した本文作業を一律にプログラム経由にしない。

1. 利用環境と対象操作に対応した管理機能を使用する。ロック取得だけを実行して終了し、その後に別の編集機能で書き込む方法を、保護済みとは扱わない。
2. 人の承認待ちや文案検討はロックの外で行う。承認は操作範囲を限定するものであり、ロックの代わりにはならない。
3. 管理機能は、取得、未完了変更の確認、最新状態・承認対象の再確認、変更、結果確認、解放を一つの処理内で行う。参照元の変更では、参照保護の検査から変更終了までを同じ保護の内側に置く。
4. 競合、確認後の変更、参照先の消失、管理表の欠落・解釈不能を検出したら、対象を変更せず返す。未完了変更がある場合も、印を消して続行しない。
5. 処理の異常終了でロックが解放されても、変更が完了・復元したとはみなさない。旧版・実体・未完了記録を保持し、確認済み状態、未実施操作、再開に必要な判断を示す。
6. 時間経過や応答の遅さだけで他の処理のロックを解除しない。機能がない、または保護を確認できない場合は単独運用に戻す。
7. 単独運用へ切り替えても、未完了変更の検出を迂回しない。旧版・実体・変更記録を照合して復元または完遂の方針を確定するまで、その変更に関わる操作を再開しない。影響範囲が不明なら共有状態を変更しない。

共通規則・ガイド・管理プログラムの更新は、対象作業を全チャットで停止した単独運用を確認してから行う。書込み時のロック取得だけでは、他のチャットが読込済みの旧規則を使わなくなったとは判断しない。停止を確認できなければWIP案までとし、更新後の再開時に規則とタスク状態を読み直す。
