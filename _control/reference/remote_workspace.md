# リモート保存と交代引継ぎ

## 基本

この手順はDriveへの保存、環境の交代、保存済みローカル複製の整理にだけ使う。ローカルだけの既存運用は変更しない。通常の作業は必要ファイルを取得した後、実際の`_control/rules.md`と既存の管理表に従う。Pythonや独自の索引解釈を基本操作の前提にしない。

Driveにも通常の相対配置と実際の名前を保つ。例えば`_control/rules.md`は、そのフォルダ直下の`_control`内の`rules.md`として保存する。`projects/<project-id>/_control/`、`current/`、`wip/`、`reference/`、`archive/`の役割と既存配置は変えない。`library/`、`profiles/`、管理プログラムや既存ソースコードも現在の相対配置を維持する。

同じ保存先への書込み担当は一つとし、人が交代を宣言する。保存・確認が終わるまで次の担当は作業を開始しない。自動同期、同時編集の調停、最後の正常な一式への自動復元はこの手順に含めない。

## 送る側：記録・保存・交代

1. 対象作業の書込みを止める。未完了タスクごとに、既存のタスク詳細のNotesへ、確認済み進捗、決定事項、未解決事項、次の操作、必要ファイルの正確な相対パス、保存先を記録する。追加・変更だけでなく、移動元と移動先、削除対象も記録する。長い時だけWIPの補足資料へ分けてリンクする。
2. 引継ぎ状況をNotesに「準備中」と記し、その詳細を保存先へ先に反映する。承認された範囲で、共通規則・必要なガイド・管理表・タスク詳細、現行成果物だけでなく必要なWIP・参照・旧版・素材も、元の配置で保存する。未変更の必要資料は保存先の実在を確認すれば再送不要。共有範囲の変更は従来の所有・承認手順に従う。
3. 保存した対象の場所・名前・形式を確認し、必要な内容・参照が欠けていないかを形式に応じて確認する。成功応答だけで内容確認済みとは報告しない。途中なら「準備中」を維持し、確認済みと不足を記録して送る側で補う。
4. 一式の保存確認後、Notesを「保存確認済み」にしてタスク詳細を最後に保存・確認する。人へ保存先、対象、再開点、残る制約を伝えて交代する。タスクのactive等は維持し、引継ぎのためにdoneへ変えない。ローカル整理の未完了と保存未完了は区別して報告する。

記録例は次のとおり。既存のNotesに追記し、新しい管理ファイルは必須にしない。

```markdown
### 環境間の引継ぎ
- 状況：準備中（確認後に保存確認済みへ変更）
- 保存先：正確なDriveフォルダURL
- 確認済み進捗・決定：…
- 未解決事項と次の操作：…
- 必要・変更ファイル：_control/context.md、wip/T-XXX_....md、current/....md
- 移動・削除：対象なし、または移動元→移動先／削除対象と承認状況
```

## 受ける側：初回

人が指定した作業領域のDriveフォルダと、新しいローカル作業場所だけを対象にする。Driveで実際の`_control/rules.md`を読み、通常配置の作業領域であることを確認する。存在しない場合は、独自索引や似たファイルから補わず、保存側の配置を確認する。

人が一式の取得を依頼した場合は、対象作業領域内のファイル名・種類を確認し、作業に必要な一式を相対配置のまま取得できる。本文を全てLLMへ読む指示ではない。`.git`、資格情報、同期アプリの設定、不要なキャッシュを無条件に含めず、リンク先の領域外へ出ない。既存ローカルルートを上書きしない。コードやスキルを取得しただけで実行・インストールしない。

取得後はローカルの`_control/rules.md`から通常の順に読み、対象project・タスクを選ぶ。引継ぎのNotesが「保存確認済み」であることと必要資料の実在・読める内容を確認し、対象タスクの入力だけを利用する。必須資料の欠落・読取不能・規則の全文未読を、取得成功で補わない。

## 受ける側：既存の作業場所

既存ルートの`_control/rules.md`から入り、同じDrive保存先の同じ作業領域であることと、交代する人の指示を確認する。保存側のタスク詳細のNotesを参照し、変更・必要ファイルと管理情報を取得し直す。ローカルに唯一の未保存編集がある場合は上書きせず、両方を保持して扱いを確認する。

不足の確認には、保存側の最新の管理表と対象タスク詳細を先に取得し、Notesの必要・変更ファイルと`context.md`の入力パスを、ローカルの実在と照合する。存在しない必要ファイルを取得し、変更対象は同名のローカルファイルがあっても取得し直す。同名ファイルの存在だけで最新版と判断しない。未保存編集があれば上記のとおり保持する。この確認は一覧の記載漏れや、一覧外の内容の古さを自動検出するものではない。

取得後は更新後の`_control/rules.md`と管理表を通常の順に読み直し、保存側Notesが「保存確認済み」であること、必要資料が揃っていることを確認して再開する。

移動・削除は記録された対象だけを扱い、一覧にないことだけでローカルから消さない。参照変更・削除の承認と従来の参照保護を省略しない。差分の識別が確実でなければ、既存の未保存内容を保持したまま新しい作業場所へ必要一式を取得する案を示す。全件の厳密な差分計算を再開の必須条件にはしない。

## Google純正形式と外部参照

Google Docs・Sheets・SlidesはDrive上の正本を直接利用できる。通常ファイルと同じ元形式でダウンロードできると仮定せず、Officeへ暗黙変換しない。取得用の書出しを使う場合は、書出し形式と正本のリンクを区別し、正本の切替は別途判断する。

ローカルのcontextに入力パスが必要な場合は、該当する`current/`等に、資料名・実形式・正確なURLまたはIDを記した小さなMarkdown案内を置き、それを登録する。案内が本文そのものだとは扱わず、利用時はリンク先の必要内容を読む。全体の所在索引は新設しない。自分たちの成果物を遠隔に置くという理由で`reference/external/`へ移さない。外部の参照資料は従来の参照記述・利用条件を維持する。

## 確認とローカル整理

通常の読取り再開では、正しい保存先・資料・必要な版であることと、必要内容が欠落なく読めることを確認する。全ファイルの元バイトハッシュを一律には要求しない。厳密な転送・復元やバイナリの一致が必要な時は、利用可能な比較・検証手段を使い、その保証範囲を報告する。

ローカルから本文を消す前は、保存先で再利用できることを形式に応じて確認する。添付・素材等が含まれる資料はその必要部分も確認し、根拠が不足する対象は保持する。消去対象は正確に列挙した保存済みの作業用複製だけ。利用中・未保存の資料、起動に必要な規則、再取得不能な実体は消さない。パス・識別子等の小さな記録と、機密を含む本文・タスク詳細を区別する。

同期アプリでローカル削除がDriveへ伝播する場所を、単なる作業用複製とみなして消さない。削除不可の場合は残存場所を報告し、同じPC内への移動だけで消去済みとはしない。保存成功とローカル整理完了は分けて伝える。

## 能力不足・失敗時

- 保存途中・内容不足：交代せず、Notesに未完了と不足を残す。保存済み対象から再送・修復を判断し、自動で旧版へ戻ったとはしない。
- ファイル取得方法が不明：確認できた対象・内容と、取得・ローカル配置の未確認を分ける。ハッシュ必須を外しても、ファイル転送自体が可能になったとはしない。
- 本文がBase64等で会話へしか返らない：その経路の入力量・転記負荷を明示する。長い本文を手で転記することを通常の一式取得方式にせず、接続手段の変更・人が用意するコピー等の代替案を提示する。未確認の代替を実行済みと報告しない。
- 取得後の普通の読取りで必要内容を完全に確認できる場合は、元バイトの直接受渡しがないことだけで利用不可としない。ただし、この結果を機械的な一式復元・安全な消去の確認へ広げない。

追加調査の前に、失敗した条件が利用者の必須要件か、方式上の追加保証かを区別する。必須要件を満たす別方式があれば案を更新する。必須要件自体を下げる必要がある時だけ、その判断を求める。
