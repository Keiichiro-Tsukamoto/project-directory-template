# Rules

## タスク開始

各タスクでは、次の順に必要なファイルだけを読む。

1. `_control/project.md`
2. `_control/tasks.md`
3. `_control/context.md`
4. activeタスクのtask detail file
5. active Task IDとして`context.md`に登録されたファイル

プロジェクト全体を勝手にスキャンしない。`current/`も常時読む場所ではない。

## 管理ファイルと状態

- `project.md`：Background、Purpose、Goal
- `tasks.md`：タスク、status、task detailの場所
- `context.md`：Task IDと読むファイルの対応
- `rules.md`：常時適用する安全核と読込ルール

管理ファイルは短く保つ。statusは`pending`、`active`、`blocked`、`done`だけを使い、`active`は最大1件とする。

各タスクは`Background`、`Purpose`、`Goal`、`Notes`を持つtask detail fileを`wip/`に作り、その場所を`tasks.md`に記載する。task detail fileは`context.md`へ重複登録しない。

task detailが表す背景、目的、成果、完了条件は、現時点で最善の作業仮説として扱う。新情報による意味を変えない明確化や事実訂正はWIPで行えるが、解く問題、意図する成果、重要なscope、承認済み方針を変える場合は、理由と影響を人へ示して承認を得る。別のタスクに相当する場合は、同じタスクを拡張し続けずタスク分割を提案する。

- `wip/`：作業中、レビュー中、承認待ち
- `current/`：承認済みの現在有効な成果物
- `reference/`：必要時だけ読む背景資料と詳細ガイド
- `archive/`：旧版、完了済み、置換済み、廃止済み

## コンテキスト

`context.md`は1ファイル1行とし、activeタスクを開始、継続、レビュー、修正、再現するために必要なファイルだけを登録する。

activeタスクの一次成果物と、検収または再現に必要なファイルを作成したら登録する。一時ファイル、キャッシュ、ログ、重複形式、自動再生成できる中間生成物は登録しない。

過去成果物を再利用する場合は、新しいTask IDで必要な現行ファイルを登録する。`archive/`は明示的に必要な特定ファイル以外は読まない。

`context.md`は、activeタスクで正式な入力として使う既存ファイルの一覧でもある。未登録の既存ファイルを、存在や名前だけを根拠に探索、読込、採用しない。

登録済み入力ではGoalを正確に達成または検証できない場合、不足情報、必要な理由、受入可能な形式をまとめて人へ提言する。人が既存ファイルの正確なパスを示したら、contextへ登録してから読む。入力が存在せず、人が別タスクでの作成を選んだ場合は、同時に複数をactiveにせず、詳細手順を運用ガイドに従う。

未完了のactiveタスクを別のセッション、サービス、LLMへ引き継ぐと人が指定した場合は、最新の再開地点を現在タスクの短いWIP引継ぎ記録へ整理し、active Task IDで`context.md`へ登録する。

タスク完了後に別環境で次タスクを開始する場合は、完了前に次のtask detailへ必要な結果と参照先を引き継ぐ。情報量が多い場合だけ次タスク側にWIP引継ぎ記録を作り、次タスク開始時にcontextへ登録する。次タスクが未確定なら、新環境は過去資料を推測で読まず、人へ開始タスクを確認する。会話履歴や製品固有のmemoryを正規入力の代わりにしない。

テンプレート更新で人が指定したプロジェクト外のローカル更新元は、正確な場所と参照を許可された相対パスを記したWIP参照記録をcontextへ登録し、更新ガイドに従って扱う。

## 作業と承認

Goalを満たすための、範囲内で回復可能なローカルWIP変更と非破壊的な検証は自律的に進めてよい。

次はユーザーまたは既存プロジェクト方針による明示的な承認を必要とする。

- WIP成果物の確定、`current/`への昇格、タスクの`done`への変更
- 外部リソースの追加、更新、削除、共有、移動
- 許可が必要な外部内容のローカル保存またはGit登録
- `.gitignore`、branch、stage、commit、push、remote、履歴の変更
- 破壊的または回復困難な操作
- 新しいトップレベルディレクトリ
- タスクの重要なスコープ拡大
- 正とする成果物や方針を決める必要がある矛盾

アクセストークン、セッション情報、認証情報、有効期限付き署名URLなどの秘密情報を、管理ファイル、参照記述、成果物、ログ、Gitへ保存しない。

外部リソースは`reference/external/`の正確な参照記述を介して登録する。参照権限を変更権限とみなさず、アクセス不能やrevision検証不能をWeb検索、類似文書、未登録キャッシュへ暗黙に置き換えない。

## ファイル配置

新規または未確定の管理文書と成果物は`wip/`へ置く。現行成果物を修正するときは`current/`を直接変更せず、入力として登録して修正版を`wip/`へ作る。

既存のソースコード、設定、テスト、アセットはプロジェクト固有の構成を維持し、必要なファイルだけをcontextへ登録する。

## 条件付きガイド

次の作業では、最初の関連操作より前に対応ガイドをactive Task IDで`context.md`へ登録して読む。

| 作業 | ガイド |
|---|---|
| 入力不足、タスク依存、ライフサイクルの例外判断、成果物昇格、タスク完了 | `reference/operation_guide.md` |
| 既存テンプレート利用プロジェクトの更新 | `reference/template_update_guide.md` |
| Git、差分、hash、`.gitignore`、成果物バンドル | `reference/git_artifact_management.md` |
| 外部リソースの取得、保存、revision、更新 | `reference/external_resource_context.md` |
| モデル選択、委譲、分業、並列化 | `reference/model_routing_and_delegation.md` |
| 複数タスクへ影響する重要な設計判断をADRへ記録 | `reference/architecture_decision_records.md` |

利用できない機能を前提にせず、各ガイドの安全境界は実行環境のsandbox、approval、memory、skillsなどで置き換えない。

## 矛盾と不明点

この会話でユーザーが明示した最新の指示を優先し、必要なら管理ファイルの更新案を出す。それ以外で内容が矛盾する場合は`rules.md`を優先する。

現在のタスク、対象、必要コンテキスト、正とする版が特定できない場合や、正しさに影響する不確実性が残る場合は推測で続けずユーザーへ確認する。小さく、正確性に影響しない不明点は最小限の仮定で進めてよい。

同じ原因の失敗に対し、結果を変える根拠のない再試行を繰り返さず、修正後も新しい情報が得られなければ停止する。

管理のための管理を増やさず、新しいメタデータ、ルール、管理ファイルは明確に必要な場合だけ追加する。
