# Rules

## 読み込み順

各タスクを始めるときは、次の順番で必要なファイルだけを読む。

1. `_control/project.md`
2. `_control/tasks.md`
3. `_control/context.md`
4. `active` タスクに対応する task detail file
5. `_control/context.md` で `active` タスクの Task ID に紐づけられたファイル

プロジェクト全体を勝手にスキャンしない。

## ディレクトリ

- `_control/`: プロジェクト管理ファイル
- `wip/`: 作業中、レビュー中、未確定のファイル
- `current/`: 現在有効なファイル
- `reference/`: 背景資料、外部資料、参考資料
- `archive/`: 旧版、完了済み、置換済み、廃止済みのファイル

`current/` は「現在有効」という意味であり、「常に読む」という意味ではない。  
読むファイルは `_control/context.md` で決める。

## 管理ファイル

- `project.md`: プロジェクトの Background、Purpose、Goal だけを書く
- `tasks.md`: タスク一覧だけを書く
- `context.md`: Task ID と読むファイルの対応だけを書く
- `rules.md`: この作業ルールだけを書く

`_control/` 配下のファイルは短く保つ。

## タスク

タスクのステータスは次の4つだけを使う。

- `pending`
- `active`
- `blocked`
- `done`

`active` は最大1件とし、そのタスクを現在のタスクとする。  
進行中のタスクがない場合は、すべてのタスクを `pending`、`blocked`、または `done` にする。

`active` は、作業中、承認待ち、修正中、再レビュー中をすべて含む。これらを別のステータスで管理しない。

各タスクは task detail file を持つ。  
task detail file は次の形式にする。

~~~markdown
# Task T-XXX: Task Name

## Background

## Purpose

## Goal

## Notes
~~~

task detail file は `context.md` には書かない。  
task detail file の場所は `tasks.md` に書く。

タスクは Goal を満たすところまで自律的に進めてよい。  
成果物の確定、`current/` への移動、タスクの `done` への変更には、ユーザーの明示的な承認を必要とする。  
承認待ちの成果物は `wip/` に置き、タスクは `active` のままにする。

## コンテキスト

`context.md` は、1ファイル1行で書く。

~~~markdown
| Task ID | File |
|---|---|
| T-XXX | current/example.md |
~~~

`context.md` には、現在作業中または近いうちに使うタスクだけを残す。  
完了済み・非アクティブなタスクの行は、原則として削除する。

`context.md` には、タスクを開始、継続、レビュー、修正、再現するために読む必要があるファイルを書く。  
activeタスクの一次成果物や再現に必要なファイルを作成したら、そのタスクの行として追加する。  
一時ファイル、キャッシュ、ログ、重複形式、自動再生成できる中間生成物は追加しない。  
レビューを依頼する前に、必要な入力と成果物が含まれ、参照先が存在することを確認する。

過去のタスクで使った成果物を別のタスクで再利用する場合は、新しいTask IDの行として登録する。

`archive/` は、明示的に必要な場合以外は読まない。  
`reference/` は、必要な場合だけ読む。

## 外部リソース

- 外部リソースは、`reference/external/`配下の正確な参照記述ファイルを介して`context.md`へ登録する。指定されたリソースと取得範囲だけを読み、外部のドライブ、サイト、フォルダ、ワークスペースを勝手に探索しない。
- 外部リソースの参照権限は書き込み権限を意味しない。追加、更新、削除、共有、移動その他の外部状態変更は、ユーザーが対象と操作を明示的に承認した場合だけ行う。
- 外部リソースの変更案は、先にローカルの`wip/`で作成して承認を受ける。承認後に外部へ反映する直前にリビジョンを再確認し、反映後のリビジョンと内容も確認する。
- 外部内容をローカルへ保存またはGitへ登録する場合は、参照記述ファイルでその操作が許可されていることを確認する。`要承認`または不明の場合は、ユーザーの明示的な承認を得る。
- アクセストークン、セッション情報、認証情報、有効期限付き署名URLその他の秘密情報を、参照記述ファイル、スナップショット、管理ファイル、成果物、ログ、Gitへ保存しない。
- 外部リソースへアクセスできない場合、または指定リビジョンを検証できない場合は、Web検索、類似文書、未登録のキャッシュへ暗黙に置き換えない。参照記述で許可された代替手段がなければ作業を停止してユーザーへ報告する。
- 一時的な取得状態は`wip/T-XXX/.tmp/external-state/`へ置き、Gitおよび`context.md`の対象外とする。検収または再現に必要な記録だけをWIPエビデンスへ昇格させ、`context.md`へ登録する。
- リモート正式版とローカルの承認済み成果物が一致しない場合は、どちらを正とするか推測せずユーザーへ確認する。

## ファイル配置

新規作成または未確定の管理文書・成果文書は `wip/` に置く。

複数ファイルからなる成果物は、原則として `wip/T-XXX/` にまとめる。キャッシュなどの一時物はその `.tmp/` に置き、`context.md` へ追加しない。

現在有効な成果物は `current/` に置く。

`current/` の成果物を修正するときは現行版を直接変更せず、現行版を入力として参照し、修正版を `wip/` に作る。  
承認後に旧現行版を `archive/` へ移し、修正版を `current/` へ移す。

背景資料や外部資料は `reference/` に置く。

旧版、完了済み、置換済み、廃止済みのファイルは `archive/` に置く。

ユーザーの承認なしに、新しいトップレベルディレクトリを作らない。

Gitが利用可能な場合、現在のタスクに関係するパスだけを対象に、読取専用の差分確認を行ってよい。
既存のプロジェクト方針またはユーザーの明示的な許可なしに、`.gitignore` の変更、branch作成・切替、stage、commit、pushを行わない。

## モデル選択と分業

- 作業には、必要条件を満たす最小コストの方法を使う。決定的なツールで検証できる処理を最初に検討し、モデル名や価格をルールへ固定しない。
- 低コストモデルまたは別エージェントへ委譲するときは、Task ID、1つの下位作業、Goal、許可する入力と出力、禁止事項、検収条件、エスカレーション条件を明示する。必要なプロジェクト規則を省略しない。
- 並列処理は1件のactiveタスク内に限定し、入力と出力が独立した下位作業だけに使う。同じファイルを複数の作業者が同時編集しない。
- 入力不足、規則の矛盾、検証不能、範囲外変更、権限操作、高影響で検証困難な判断が必要になった場合は、推測で続けず上位モデルまたは人へエスカレーションする。
- モデル階層にかかわらず、成果物確定、外部書き込み、Git変更操作などの既存の承認規則を維持する。

## 適用範囲

このディレクトリ構成は、コンテキスト管理と文書成果物の標準として使う。

既存のソースコード、設定ファイル、テスト、アセットなどは、プロジェクト固有の構成を維持する。  
それらを `wip/` や `current/` へ移動せず、現在のタスクで必要なファイルだけを `context.md` に書く。

## タスク完了時

ユーザーが成果物を承認し、タスクが完了したら、次を行う。

1. `tasks.md` のステータスを `done` にする
2. task detail file を `archive/` に移す
3. `context.md` から不要な行を削除する
4. 継続利用する成果物を `current/` に移す
5. 不要になった作業ファイルや旧版を `archive/` に移す
6. 後続タスクが移動した成果物を参照している場合は、`context.md` のパスを更新する

## 矛盾と不明点

会話履歴と `_control/` の内容が矛盾する場合は、原則として `_control/` を優先する。

`rules.md` と他の管理ファイルまたは成果物が矛盾する場合は、`rules.md` を優先する。

ただし、ユーザーがこの会話で明示的に更新を指示した場合は、その指示を優先し、必要な `_control/` ファイルの更新案を出す。

次の場合は、作業を進める前にユーザーへ確認する。

- 現在のタスクが不明
- 対象ファイルが不明
- 必要なコンテキストが不足している
- 古いファイルが参照されている可能性がある
- プロジェクト構造やルールを変更する必要がある

小さな不明点で、正確性に大きく影響しないものは、最小限の仮定を置いて進めてよい。

## 小さく保つ

管理のための管理を増やさない。

新しいメタデータ、ルール、管理ファイルは、明確な必要がある場合だけ追加する。

履歴、経緯、長い説明は、毎回読む管理ファイルには入れない。
