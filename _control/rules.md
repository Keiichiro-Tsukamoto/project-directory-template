# 作業領域の規則

## 全体像

このファイルは`<作業領域ルート>/_control/rules.md`にある。`_control/`の親から下のディレクトリ全体を作業領域と呼び、ルートを`workspace:`と表す。`workspace:_control/rules.md`はこのファイルを指す。実際のファイル操作では、この表記を作業領域ルートからのパスへ解決する。

ファイルを開く権限があっても、作業の入力として読む許可があるとはみなさない。本規則の起動手順と、選択したタスクの`context.md`に従って読む。アクセス権限を変更しない。

| 場所 | 役割 |
|---|---|
| `workspace:_control/` | 共通規則、作業領域管理タスク、共通ガイド、管理プログラム |
| `workspace:projects/<project-id>/` | 独自の背景・目的・目標とタスクを持つproject。ディレクトリ名がProject ID |
| `workspace:library/` | 作業領域内の全projectに共通利用させる知識・資料・クエリ・スキル。少数project間の再利用だけでは昇格しない |
| `workspace:profiles/<profile-id>/` | 利用者固有の手順・判断基準・素材・スキル |

共通規則はこのファイルに一組だけ持つ。project固有の制約は当該`_control/project.md`の必要時だけ設ける「制約」節に記載する。詳細資料へ分ける場合は、必要な操作と正確な参照先を同節に記す。独自の規則体系を増やさず、共通規則との矛盾は人へ確認する。

`wip/`は作業中、`current/`は承認済みの現行成果物、`archive/`は旧版・完了資料、`reference/`は必要時だけ読む参照資料を置く。具体的な配置は[2節](#2-所有範囲とパスを固定する)に従う。

本規則の「管理表」は`tasks.md`、`context.md`、`dependencies.md`の総称。「タスク詳細」は`tasks.md`の`Detail`が指定するファイル。「正規入力」は対象タスクの`context.md`に登録した既存ファイルを指す。各列の意味は[4節](#4-管理表が表すもの)に従う。

## 1. 作業範囲を選ぶ

タスクの内容を解釈する前に、どのprojectまたは作業領域管理を対象とするかを決める。

1. 人がProject IDまたは正確なprojectパスを指定した場合は、その場所を確認する。存在しない、名称だけで一意でない、指示が矛盾する場合は人へ確認する。
2. 同じセッションで選択済みの対象は、切替指示がなければ維持する。新規セッションで以前の会話を推測して補わない。
3. 対象未選択なら、人へ選択を求める前に、次の順で案内を作る。
   1. `workspace:projects/`直下のディレクトリ名を取得し、各`_control/project.md`の`Purpose`を読む。候補案内のために許可する取得範囲はこの二つだけである。
   2. 既存projectのProject IDと目的の一文を一覧で示す。目的が未定義なら「目的未設定」、定義ファイルを読めなければ「目的を取得不能」と示し、別資料で補わない。projectがなければ「既存projectなし」と示す。
   3. その一覧と「新規project作成」「作業領域管理」を示して対象の選択を求め、回答を待つ。候補を示さずProject IDだけを質問して終わらない。
4. 人が対象を選んでから次節へ進む。正確な対象が既に指定されていれば、全一覧を作らずその対象だけを読む。

見出し単位の取得ができない場合、選択案内では各`project.md`だけを取得できる。他の管理表、WIP、成果物を読まない。projectがゼロでも正常な初期状態である。

projectの作成・取込・持出し・削除、共通規則、`library/`、`profiles/`の変更は作業領域管理で行う。新規project作成は人の作成依頼を承認として扱い、同じ承認を重ねて求めない。作成したprojectの背景・目的・目標を定義する作業は、そのprojectのT-001で行う。`project.md`を編集するという理由だけで作業領域管理へ切り替えない。

## 2. 所有範囲とパスを固定する

選んだ範囲に応じ、次の対応を使う。以下の「管理範囲」は、この表の一列だけを指す。

| 対象 | project作業 | 作業領域管理 |
|---|---|---|
| 管理範囲のルート | `workspace:projects/<project-id>/` | `workspace:_control/` |
| 定義 | `workspace:projects/<project-id>/_control/project.md` | 専用の定義ファイルは作らない |
| タスク一覧 | `workspace:projects/<project-id>/_control/tasks.md` | `workspace:_control/tasks.md` |
| 入力一覧 | `workspace:projects/<project-id>/_control/context.md` | `workspace:_control/context.md` |
| 通常の作業場所 | `workspace:projects/<project-id>/wip/` | `workspace:_control/wip/` |

`tasks.md`の`Detail`は管理範囲ルートからの相対パス。`context.md`の`File`は同じ範囲なら相対パス、別範囲なら`workspace:`付きパスとする。OS上の絶対パスと`..`は保存しない。例えば`wip/T-001_note.md`は、project作業ではprojectルート配下、管理作業では`workspace:_control/`配下を指す。

管理タスクの詳細・候補・検証資料は`workspace:_control/wip/`に集約する。`library/wip/`と`profiles/<profile-id>/wip/`を作業場所にしない。

| 対象 | 確定後の配置 |
|---|---|
| 完了した管理タスクの詳細・必要な制作記録 | `workspace:_control/archive/` |
| 管理作業の不要物を削除できない時 | `workspace:_control/archive/discarded/<Task ID>/` |
| 全project共通成果物の現行版・旧版 | `workspace:library/current/`、`workspace:library/archive/` |
| 利用者固有成果物の現行版・旧版 | `workspace:profiles/<profile-id>/current/`、`workspace:profiles/<profile-id>/archive/` |
| 共通規則・ガイド・管理プログラム | `workspace:_control/rules.md`、`workspace:_control/reference/`、`workspace:_control/tools/`内の指定先 |
| projectの管理文書 | `workspace:projects/<project-id>/_control/`内の指定先 |
| 既存ソースコード・設定・テスト・素材 | 登録された現在のパス。`current/`へ一律に移さない |

`workspace:_control/current/`は設けない。共通規則等の旧版を保管する場合は管理タスクの`archive/`に置く。projectの通常成果物は当該projectの`current/`、旧版と完了資料は`archive/`へ置く。他projectの現行成果物の変更は、そのprojectのタスクが所有する。

## 3. タスクを選び、必要な入力を読む

1. project作業なら、上表の定義ファイルを読む。背景・目的・目標が未確定の場合は、初期化タスクだけを扱う。
2. 選んだ範囲の`tasks.md`を読み、下表で対象を決める。
3. 同じ範囲の`context.md`を読み、対象Task IDの行だけを選ぶ。
4. 対象行の`Detail`にあるタスク詳細を読む。
5. 登録済みの業務本文を読む前に、依頼・タスク詳細・入力一覧から今回の操作を確認し、[9節](#9-操作ごとに読むガイド)で該当するガイドだけを登録して読む。外部資料はローカル保存済みの本文も対象とする。
6. 対象タスクが`active`で、該当ガイドの利用条件を満たしたら、必要な登録済み本文だけを使用直前に読む。登録済みという理由で本文を先読みしない。

この規則と、選択した管理範囲の定義・管理表・対象タスクの詳細は、起動時のcontext登録を不要とする。他範囲の定義・詳細へこの例外を広げない。他範囲の表等を確認できるのは、本規則やガイドが操作と対象を明示した場合だけである。表の`Detail`から他範囲の詳細を読む時は、完了済みでも利用側タスクへ正確なパスを登録してから読む。必須ファイルが欠けていれば、別projectのファイルで代用せず、不足を示す。新規作成・取込の途中なら、その管理タスクの手順で作成・修復する。

タスク指定の有無にかかわらず、同じ範囲に`active`が複数あれば一覧の矛盾として停止する。それ以外は次の表を使う。

| 状態・依頼 | 行動 |
|---|---|
| タスク未指定、`active`が一件 | そのタスクを継続する |
| タスク未指定、`active`がゼロ | 開始候補を人へ示す。登録順で選ばない |
| 指定タスクが`active` | そのタスクを継続する |
| 指定タスクが`pending`で開始を依頼され、他の`active`がない | 目標と入力条件を確認して`active`にする |
| 指定タスクが`blocked`で再開を依頼された | 詳細の停止理由を読み、解消と他の`active`がないことを確認して再開する |
| 別のタスクが`active`のまま新しいタスクの開始を求められた | 下記の登録・切替手順に従う。無断で置換しない |
| 依頼された新規タスクが未登録 | 下記の登録・切替手順に従う。登録と開始を分ける |
| 指定タスクが`done` | 指定行の`Detail`から完了記録を読む。追加作業がある場合だけ新規タスクを作る。完了状態を巻き戻さない |

新規登録・切替では、`workspace:_control/reference/operation_guide.md`の[「タスクの登録と切替」](reference/operation_guide.md#タスクの登録と切替)を登録して読み、次の順に進める。

1. 新規依頼の目的と必要成果を確認し、詳細と`pending`行を作る。既存タスクの状態は変えない。登録済みなら重複作成しない。
2. 登録だけの依頼なら終了する。開始も依頼された場合、既存`active`の中断・完了を確認する。既に明示された同じ指示は確認し直さない。
3. 中断なら既存詳細へ理由・再開条件を記録し、既存タスクを`blocked`にして入力行を保持する。完了なら通常の承認・完了処理を終える。
4. 他の`active`がないこと、新タスクの目標と開始条件を確認して`active`にする。開始条件を満たさなければ`pending`のまま不足を示す。中断済みの旧タスクを勝手に再開しない。

完了資料を再利用する時は、指定された`Detail`の`Notes`にある成果物の最終配置から必要なファイルを選び、新Task IDのcontextへ登録して本文を読む。記録・実体がない、現行版が不明な場合はパスを人へ確認する。完了記録を現在版への自動リンクとみなさない。

状態・詳細の確認やレビューだけを依頼された場合は、指定資料を必要な範囲で読み、状態を変えない。停止中・開始待ちタスクの業務入力を一括で先読みしない。

## 4. 管理表が表すもの

| ファイル・列 | 意味 |
|---|---|
| `project.md`の`Background / Purpose / Goal` | 背景、目的、達成する目標 |
| `tasks.md`の`Task ID / Name / Status / Detail` | 範囲内で一意なID、人向け名称、状態、詳細の場所 |
| `context.md`の`Task ID / File` | そのタスクで利用できる正規入力一ファイル。読込許可であり一括読込指示ではない |
| `workspace:_control/dependencies.md`の`Consumer / Source` | 現行成果物が別範囲の実体を継続して必要とする関係。削除・移動・置換前の影響確認に使う |

状態は`pending`（開始待ち）、`active`（作業・レビュー・承認待ち）、`blocked`（理由を記録して停止）、`done`（承認・完了処理済み）の四つ。`active`は管理範囲ごとに最大一件。別範囲の`active`は競合とみなさない。

タスク詳細は`Background / Purpose / Goal / Notes`を持ち、未完了時は`wip/`、完了後は`archive/`へ置く。対象タスク自身の詳細はcontextへ重複登録しない。他範囲のタスク詳細を入力に使う場合は登録する。範囲をまたいでIDを示す場合は`workspace#T-001`や`projects/<project-id>#T-001`とする。

contextには、同じ管理範囲の`tasks.md`で`pending / active / blocked`となっているTask IDの入力行を保持できる。状態はTask IDで`tasks.md`と照合し、contextに状態列を重複して持たない。`pending`は開始待ち、`blocked`は再開用の保持であり、未作成パスの予約ではない。対応するTask IDがない行や`done`の行は不整合として扱う。完了前に必要な後続参照を引き継いでから、対象タスクの行を除く。

## 5. 入力と作業

未登録の既存ファイルを、存在や名前だけを根拠に探索・読込・採用しない。人が示した正確なパスは対象タスクへ登録してから読む。規則が指定する条件付きガイドも同様に扱う。`current/`、`reference/`、`archive/`を一括で読まない。

一次成果物、レビュー・再現・検収に必要な資料は作成後に登録する。一時ファイル、キャッシュ、不要なログ・重複形式、再生成できるだけの中間物は登録しない。未読内容を引用・推測しない。引継ぎは詳細に示された登録済みの正確なパスから再開し、会話履歴や製品固有の記憶で代用しない。

次の場合は、表の順で対処する。

| 状況 | 行動と再開条件 |
|---|---|
| 必要な入力がない | 不足情報・必要な理由・受入可能な形式を人へ示す。その入力を要する判断は進めない |
| 依頼の一部だけが実施不能 | 独立してできるWIP作業を進める。残る不足を記録する |
| タスク全体を続行できない | `blocked`にし、詳細の`Notes`に理由・再開条件を残す |
| 事実や表現の訂正 | 目的・成果・承認範囲を変えなければWIPを訂正する |
| 目的、必要成果、重要な範囲、確定方針が変わる | 根拠と影響を示し、人の判断後にタスク定義を更新する |

新規・修正版は`wip/`で作る。現行文書は入力として登録してから修正版を用意する。既存ソースコード・設定・テスト・素材はproject固有の配置を維持する。別範囲のWIPは、人が指定したレビュー候補として扱い、確定した現行版とみなさない。

## 6. 承認を判定する

| 操作・発話 | 扱い |
|---|---|
| 目標の範囲内で回復可能なWIP作業、非破壊的な検査 | 進めてよい |
| 成果物確定、現行化、タスク完了 | 対象と操作の明示的承認が必要 |
| 共有・他projectへの反映、外部変更・共有、許可が必要な保存 | 対象と操作の明示的承認が必要 |
| Git変更、削除等の破壊的操作、新しい最上位ディレクトリ | 対象と操作の明示的承認が必要 |
| 質問、レビュー、成立条件、修正提案 | WIPの検討・修正へ反映する。採用・反映の承認には読み替えない |
| 同じ対象と操作が既に承認済み | 前提が変わらなければ重ねて承認を求めない |

言及順、回数、長さから優先順位を推測しない。発話の解釈が曖昧な時は、`workspace:_control/reference/operation_guide.md`の[「レビュー、指示、意思決定の分離」](reference/operation_guide.md#レビュー指示意思決定の分離)を登録して読む。

人の最新の明示的指示を優先する。規則とprojectの制約に矛盾がある場合は、影響する操作を止めて差異を示す。閲覧権限を保存・変更権限とみなさない。秘密情報、認証情報、セッション情報、有効期限付き署名URLを管理ファイル、成果物、ログ、Gitへ保存しない。

## 7. 共有と参照保護

別projectの成果物を継続して再利用する場合は、`workspace:_control/reference/operation_guide.md`の[「project間の固定複製」](reference/operation_guide.md#project間の固定複製)を登録して読む。必要部分の固定複製を利用側projectの`reference/`へ置き、その複製を入力にする。元の正確なパス、取得時点、確認できた版情報を残す。複製は元資料の最新版を意味せず、自動同期しない。更新が必要な時は利用側タスクで新版の候補を作り、確認・承認後に切り替える。

一時的な読込・レビューと継続利用を区別する。複製の完結性・保存許可を確認できなければ、独立して利用できるとは扱わない。直接参照を続ける例外は、元の削除から保護できないことを示して人へ確認する。

`library/`への昇格は、全projectに共通利用させると明示的に判断した時だけ行う。複数projectが使うことや共同編集したいことだけを理由に昇格させない。共有候補は元projectのWIPで作れ、管理タスクへ引き継いだ候補は`workspace:_control/wip/`に集約する。反映は管理タスクが所有する。元タスクは、必要な資料の引継ぎと参照の存続を確認してから完了できる。

依頼済みの共有検討をルートの`pending`・詳細・入力行へ登録する操作と、自成果物の依存行更新は、`workspace:_control/reference/operation_guide.md`の[「共有依頼と依存更新」](reference/operation_guide.md#共有依頼と依存更新)に従う。これをルートタスクの開始や共有成果物の反映と扱わない。

参照元の削除・移動・置換前は`workspace:_control/reference/operation_guide.md`の[「参照元の削除・移動・置換」](reference/operation_guide.md#参照元の削除移動置換)を登録して読む。この検査に限り、`projects/`直下の名前、ルートと各projectの`tasks.md / context.md`、ルートの`dependencies.md`を確認できる。表を取得・解釈できなければ、参照ゼロと判定しない。

`dependencies.md`は操作前の影響確認に使う記録であり、Finder等からの直接削除を防がない。利用前にも入力の存在を確認する。固定複製は元projectの削除に備えるもので、複製先や作業領域全体の消失まで保護しない。

依存は最新追随や内容の妥当性を保証しない。別範囲にある固定旧版を使い続ける場合も依存は残る。独立した複製へ承認・切替・検証が完了して元の実体が不要になった時だけ、元の依存を解消する。

異なるprojectの独立した作業は並行できる。ただし同じ作業領域への並行書込みは、対象操作が共通の排他手順に接続済みで、利用環境でその効力を確認できる場合に限る。未接続・未確認の場合は、人が他の書込みを止めた単独運用で行う。`active`件数をロックとみなさない。並行書込みを行う前に、`workspace:_control/reference/operation_guide.md`の[「並行操作の保護」](reference/operation_guide.md#並行操作の保護)を登録して読む。

## 8. 確定と完了

承認済み成果物と、再現・検証に必要な制作記録を分けて配置する。文章の構成・表現・編集方法は、選択した文書作成スキルに従う。

完了処理は`workspace:_control/reference/operation_guide.md`の[「タスク完了時の確認」](reference/operation_guide.md#タスク完了時の確認)を登録して読み、次の順に進める。

1. 最後に承認された目標・完了条件と、実際の成果・検証結果を照合する。未達を完了としない。
2. 成果物確定・反映・タスク完了について、必要な承認の対象と範囲を確認する。
3. 参照保護と後続タスクへの引継ぎを確認し、[2節](#2-所有範囲とパスを固定する)の現行・旧版・完了記録の配置へ移す。再利用対象の成果物の最終配置をタスク詳細の`Notes`へ正確なパスで残す。
4. 不要物は削除可能なら削除する。削除権限がなければ再試行せず`archive/discarded/<Task ID>/`へ移動する。隔離物はcontextへ登録しない。
5. タスク詳細を所有範囲の`archive/`へ移し、`Detail`と残る入力・依存の参照先を更新する。対象タスクのWIPと壊れた参照が残っていないか確認する。
6. 対象タスクのcontext行を整理し、`Status`を`done`へ変更する。反映した結果を再確認して報告する。

途中で失敗した場合は`done`と報告せず、実施済み操作と残作業を詳細に残す。回復手順が未確定なら推測で削除・上書きしない。

## 9. 操作ごとに読むガイド

最初の関連操作前に、次のガイドを対象タスクのcontextへ登録して読む。新規登録・切替の入口では、同じ範囲に既存の`active`があればそのタスクへ、なければ登録済みの開始対象タスクへ登録する。どちらも存在しない初期登録の場合だけ、登録に必要なガイドを先に読める。新タスクの登録後、そのタスクにも必要なガイドを登録する。この例外で業務入力を先読みしない。

| 操作 | ガイド |
|---|---|
| 入力不足・タスク切替・引継ぎ・完了・隔離・共有依頼・依存更新・project管理・共通規則／ガイド／管理プログラムの更新 | [`workspace:_control/reference/operation_guide.md`](reference/operation_guide.md) |
| 外部参照記述の作成・外部資料の利用（ローカル保存本文を含む）・取得・保存・鮮度確認・更新 | [`workspace:_control/reference/external_resource_context.md`](reference/external_resource_context.md) |
| Git・ハッシュ・差分・成果物の一式化 | [`workspace:_control/reference/git_artifact_management.md`](reference/git_artifact_management.md) |
| モデル選択・委譲・分業・並列化 | [`workspace:_control/reference/model_routing_and_delegation.md`](reference/model_routing_and_delegation.md) |
| 複数タスクへ影響する判断の記録 | [`workspace:_control/reference/architecture_decision_records.md`](reference/architecture_decision_records.md) |

更新・フィードバック等のスキルは、人が指定したもの、または利用可能な説明から一意に選べたものだけを読む。所在不明なら正確なパスを確認する。未登録の全スキルを探索・読込しない。スキルは本規則を緩和しない。

外部資料の読込順は、上表の外部参照ガイドの[「本文利用前の確認」](reference/external_resource_context.md#本文利用前の確認)に従う。未登録の作業領域外を探索・操作しない。projectの持出しは`workspace:_control/reference/operation_guide.md`の[「projectの取込と持出し」](reference/operation_guide.md#projectの取込と持出し)に従い、現在の作業領域内で資料と手順を準備するところまでとする。

モデル選択・委譲を行わない通常作業では、そのガイドを読む必要はない。利用できない上位モデルへの委譲を前提として作業を進めない。

## 10. 確認できたことだけを報告する

報告では、実施した確認、その結果、未確認事項、残作業を区別する。実行していない検証を合格とせず、手動確認をプログラムによる検証と呼ばない。

停止時は、確認済み事実、不足する条件、再開に必要な入力・判断を示す。同じ原因の失敗を、新しい根拠なしに繰り返さない。
